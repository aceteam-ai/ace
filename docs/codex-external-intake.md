# Codex external tool-output intake

`CodexNativeHarnessAdapter.deliverExternalOutput` is the native intake
foundation for issue #19. It accepts an already journaled delivery for the exact
Ace-managed session identity and uses Codex app-server `turn/start` with
`input: []` and `toolOutput`. It never uses `turn/steer`, creates a user
message, starts another Codex process, resumes a stopped session, or changes
native approval and sandbox settings.

The tested capability is exact Codex CLI `0.154.0`, using the
non-experimental v2 JSON schema generated by:

```sh
codex app-server generate-json-schema --out /tmp/ace-codex-0154-schema
```

The generated `TurnStartParams` requires `threadId` and `input`, accepts an
optional `TurnToolOutput { name, namespace?, output }`, and represents persisted
output as a `functionCallOutput` item. The official app-server reference also
documents that a tool output submitted during a regular active turn is queued
for that turn.

## Authority and provenance

The caller supplies a stable `deliveryId`, a separate peer identity, and peer
content. Ace fixes the native tool identity to:

```json
{
  "name": "peer_message",
  "namespace": "aceteam.external"
}
```

The output string is a JSON envelope with type `aceteam.peer_message`, the
delivery ID, peer source fields, and the content. Peer content cannot select the
tool name, become user input, resolve an approval, or alter native permissions.
Instructions inside peer text therefore retain external/tool authority only.

Calling this method is the explicit native submission boundary. It does not
decide whether automatic delivery is enabled, consume an external transport, or
own the durable S6 journal. Until the #18 consumer contract exists, notification
and manual review remain above this adapter. A future consumer must check pause,
per-session opt-in, and turn/budget policy before invoking this method.

## Delivery evidence

Observers receive `external.output.status` events with these distinct states:

| Status | Evidence |
| --- | --- |
| `received` | The adapter validated and retained the delivery in this connection. No native write is claimed. |
| `submitted` | The complete JSON-RPC request frame was accepted by the owned app-server stdin stream. |
| `confirmed_accepted` | The correlated `turn/start` response identified the native turn. |
| `processed` | A matching persisted `functionCallOutput` item was observed for the native turn. |
| `unsupported` | Codex conclusively rejected the documented method or parameters. Keep the delivery available for manual review. |
| `unknown` | Submission may have reached Codex, but no conclusive response survived. Do not replay automatically. |

Idle delivery reserves and starts the one native turn before any asynchronous
write. Busy delivery uses Codex's native queue on the existing turn and does not
clear or answer pending approvals. Submissions are serialized. Repeating a
`deliveryId` returns the prior evidence with `duplicate: true` and never writes
again, including after an unknown result.

Transport failure after submission is surfaced as `unknown` with
`retrySafe: false` and terminates the local connection under the existing
fail-closed protocol rules. A native method/parameter rejection is
`unsupported`; an idle reservation is released because rejection proves that
Codex did not accept the turn.

## Verification boundary

Synthetic tests cover idle submission and persisted provenance, busy queuing
with a live approval, duplicate notification, stale thread identity, unsupported
native intake, lost-response ambiguity, and peer text that asks to approve tools.
They use authored protocol fixtures and no credentials or model calls.

No native-auth smoke test was run. The synthetic evidence proves request shape,
correlation, and adapter state behavior; it does not claim live wake support or
complete issue #19 transport/policy integration.
