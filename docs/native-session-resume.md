# Explicit managed native session resume

The integration for [#15](https://github.com/aceteam-ai/ace/issues/15)
uses the #14 shared native panel and its existing adapter contract. The manager
adds local registration and ownership; it does not reduce or persist view state.

## Product boundary

Construct `NativeSessionManager` with a local store and adapter factories, and
inject `manager.createAdapter("codex", {onNotice})` into the native panel service.
The factory receives that same store for the Codex adapter's independent resume
checks. All product session starts and resumes use this boundary.

A managed start reserves its local ID, snapshots workspace identity, and invokes
native start once. After native identity is confirmed, it acquires local ownership
before registration or publishing the opening result. Registration failure leaves
the already-created native session usable with an actionable notice; no native
start or turn is repeated. An ownership collision or unknown ownership closes the
new connection. A native adapter that opens without a confirmed native ID remains
usable with an explicit registration-unavailable notice; Ace never guesses an ID.

`listCandidates(workspace)` reads only bounded local registrations. It checks the
configured provider's resume capability, canonical workspace identity, and local
ownership. It does not start a process, authenticate, or read native previews or
transcripts. Current native version/authentication/history checks happen only on
explicit resume. Unavailable entries include a reason. The shared UI can explicitly
forget an unowned registration or quarantine corrupt state into a private backup;
unsafe files and stale shared locks retain their documented recovery requirements.

`ResumeSessionCommand.registeredSessionId` names the original saved local record.
The command's `sessionId` must be a fresh connection identity, while
`nativeSessionId` must exactly match the saved record. The manager resolves the
record and acquires local ownership before calling native resume. Active or unknown
owners block; an absent owner PID can be recovered only on this explicit action.
Resumed connections retain the original registration rather than appending another
record for each incarnation. There is no automatic restart, turn submission,
command replay, approval restoration, or new transcript store.

## Codex 0.153.4 verification

The offline non-experimental v2 schemas generated by tested Codex CLI 0.153.4
support the [documented native thread lifecycle](https://learn.chatgpt.com/docs/app-server).
The adapter independently resolves the original record and exact native identity
before spawning. It checks the installed version, initializes the owned stdio
app-server, and checks current native authentication through `account/read`.

It requests `thread/read` with `{threadId, includeTurns: false}` to inspect native
metadata. Required metadata includes the exact native ID, matching workspace,
non-ephemeral history, tested creator version, supported history format, and
`notLoaded` or `idle` status. It then requests exactly
`thread/resume` with `{threadId, excludeTurns: true}`. No cwd, model, sandbox,
approval policy, config, transcript, path, or instruction overrides are forwarded.

The resume response must confirm the same identity/workspace and effective cwd,
supported native metadata, and `idle` status. Effective native permissions are
shown using the same permission context as a new session. Local registration and
workspace are rechecked before native resume and before publishing readiness.
Unexpected startup work or approval requests fail without resurrecting grants.
Missing history, auth, unknown status, or incompatible versions are recoverable
errors; they never fall back to starting or replaying a turn.

A native `notLoaded` status describes the current app-server and does not prove
another process is absent. Cross-process ownership is enforced by the managed
product boundary. A raw Codex adapter verifies registration and native eligibility,
but does not claim to exclude other processes. Non-Ace native clients remain under
the native harness's own authority.

## Cancellation and verification

The UI observes only after managed opening succeeds; commands are blocked during
opening. Cancellation disposes the reserved identity and any late successful
native identity, without registering or submitting pending text. A registration
that committed during cancellation is removed after confirmed cleanup when the
store remains available. A storage failure reports its recovery notice instead of
silently repeating a side effect.

Native disposal is awaited before ownership release. Simultaneous close calls
share cleanup; earlier cleanup acknowledgments cannot discharge a later native
opening result. Unconfirmed or throwing cleanup retains ownership and the local
connection for a later explicit close. Cleanup uses the reserved provider/local
identity even if an adapter returns an unrelated identity.

Synthetic tests cover native resume protocol fields, missing/changed metadata,
current auth/version, stale approvals, startup cancellation, clean and abrupt
restart, corrupt state, active/unknown/dead ownership, late native success,
concurrent disposal, failed cleanup, and no implicit turn submission. No real
model or credentialed session is required by these tests. The [shared terminal chooser](native-sessions.md) lists local candidates, requires
explicit resume selection, displays registration notices, and provides confirmed
forget/quarantine recovery with scrollable full paths and reasons. UI teardown
also awaits local storage operations that the user already confirmed. Synthetic
UI and two-process PTY checks verify the user-facing restart flow.
